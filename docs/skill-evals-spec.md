# ТЗ и спецификация: eval-библиотека для скиллов (askill-evals)

**Версия документа:** 0.1 (draft)
**Статус:** предложение к реализации; дополняет основную спеку ([skills-library-spec.md](skills-library-spec.md), v1.1)
**Стек реализации:** тот же, что §4.1 основной спеки — Python 3.12+, uv, pydantic v2, pytest; плюс headless Claude Code (`claude -p`) как исполняемый бэкенд

---

## 1. Назначение и цели

### 1.1 Проблема

Скилл — это поведенческая программа для агента, но сегодня в репозитории нет ни
одного артефакта, проверяющего, что скилл работает: что он срабатывает на свои
триггеры (и не срабатывает на чужие), и что агент, прочитав его, действительно
следует ключевым правилам. Правка `description` или тела скилла — это
изменение поведения без теста: регрессию заметит только пользователь.

Методологически это та же дисциплина, что TDD для кода: пока не видел, как
агент фейлится *без* скилла (baseline), не знаешь, чему скилл на самом деле
учит; пока не прогнал сценарии *со* скиллом, не знаешь, что правка ничего не
сломала.

### 1.2 Что строим

Eval-библиотека: формат описания проверочных сценариев для каждого скилла
(`evals/<name>/suite.yaml`), раннер, который исполняет их против реального
агента и судит результат, и CI-интеграция с разделением «дешёвая статическая
валидация на каждом PR» / «LLM-прогоны по требованию».

### 1.3 Ключевые цели

- **Каждый скилл тестируем.** У скилла есть suite с минимальным покрытием:
  позитивные и негативные триггер-тесты плюс хотя бы один комплаенс-сценарий.
- **Регрессии ловятся при правке.** Изменил `SKILL.md` / `description` →
  прогнал suite → увидел, что сломалось, до публикации новой версии.
- **Детерминированное ядро.** Как и в CLI: загрузка suite, ассерции, скоринг и
  отчёт — чистые, типизированные, покрытые юнит-тестами модули; вызовы LLM
  изолированы за транспортным интерфейсом и мокаются в тестах.
- **Стоимость под контролем.** LLM-прогоны не входят в обязательный PR-цикл;
  бюджет (модель, ходы, повторы) задаётся в suite и ограничивается раннером.

### 1.4 Не-цели v1

- Общий бенчмарк агентов или сравнение моделей — судим только скиллы этой
  библиотеки.
- Статистическая значимость: по умолчанию один прогон на сценарий
  (`--repeat N` для ручной оценки разброса), без доверительных интервалов.
- GUI / web-отчёты; отчёт — JSON + человекочитаемая сводка в stdout.
- Оценка скиллов вне этого монорепо.

## 2. Глоссарий

| Термин | Значение |
|---|---|
| **Suite** | `evals/<name>/suite.yaml` — полный набор сценариев одного скилла. |
| **Сценарий** | Один проверочный кейс: prompt (+ опц. фикстура окружения) и критерии оценки. |
| **Триггер-тест** | Сценарий, проверяющий *срабатывание*: должен ли скилл активироваться на данный prompt. Бывает позитивный и негативный. |
| **Комплаенс-тест** | Сценарий, проверяющий *следование*: выполняет ли агент ключевые правила тела скилла, когда скилл активен. |
| **Baseline (RED)** | Прогон комплаенс-сценария БЕЗ скилла — документирует поведение, которое скилл должен изменить. |
| **Ассерция** | Атомарная проверка результата прогона: детерминированная (файл, grep, git) или модельная (judge). |
| **Judge** | LLM-оценщик, который судит транскрипт/воркспейс по рубрике и возвращает pass/fail с обоснованием. |
| **Раннер** | `installer/scripts/run_evals.py` — точка входа; исполняет suites и печатает отчёт. |
| **Транскрипт** | Полный лог прогона агента (JSON от `claude -p --output-format json` / stream-json). |
| **Фикстура** | Снимок воркспейса (`evals/<name>/fixtures/<id>/`), копируемый во временную директорию перед прогоном. |

## 3. Расположение и связь с репо

```
evals/
  <skill-name>/
    suite.yaml          # сценарии и пороги (формат — §4)
    BASELINE.md         # краткая сводка baseline-поведения (методология — §6)
    fixtures/           # опционально: стартовые воркспейсы для сценариев
      <fixture-id>/...
```

`evals/` живёт в корне репо рядом с `catalog/` и подчиняется тому же принципу,
что и каталог: **вне `skills/`**, значит никогда не устанавливается
пользователю и не влияет на чексумму скилла. Правка suite не требует bump
версии скилла.

Связь имён — тот же контракт, что у каталога: `evals/<name>/` ↔
`skills/<name>/` ↔ `catalog/<name>.yaml`.

## 4. Формат suite.yaml

```yaml
skill: learning-mode          # = имя папки; валидируется
version_tested: 0.1.1         # версия SKILL.md, под которую писались сценарии;
                              # расхождение с фактической -> warning в отчёте

budget:                       # верхние границы на КАЖДЫЙ сценарий
  max_turns: 8                # ходов агента в headless-прогоне
  model: claude-sonnet-4-6    # модель прогона; judge-модель задаёт раннер

trigger:
  positive:                   # скилл ДОЛЖЕН сработать
    - id: coach-me
      prompt: "Coach me on Python decorators while we build this retry helper."
    - id: due-review-on-session-start
      prompt: "Let's add a search endpoint to the users API."
      fixture: with-due-topic        # репо уже содержит .claude/learning/ с просроченной темой
  negative:                   # скилл НЕ должен сработать
    - id: just-ship
      prompt: "Write the retry decorator for me, I don't want to practice."
    - id: factual-question
      prompt: "What does functools.wraps do?"

compliance:
  - id: handoff-leaves-gap
    prompt: "Teach me Pydantic validators while we build the User schema."
    fixture: fastapi-mini
    assertions:
      - kind: file_exists
        path: .claude/learning/active-task.md
      - kind: grep
        glob: "**/*.py"
        pattern: "🎓 LEARNING TASK"
        expect: present
      - kind: judge
        rubric: >
          The assistant must NOT have written the body of the function it
          handed off to the user. A scaffold/stub or a sibling worked example
          is allowed; the handed-off gap itself must be left unimplemented.
  - id: closeout-strips-anchor
    prompt: "...multi-turn script, см. §5.3..."
    turns:                                  # многоходовый сценарий
      - "Teach me validators on this schema."
      - "{{submit: user fills the stub correctly}}"
      - "Done, review it."
    assertions:
      - kind: grep
        glob: "**/*"
        pattern: "🎓 LEARNING TASK"
        expect: absent
      - kind: file_absent
        path: .claude/learning/active-task.md

thresholds:                   # порог прохождения suite
  trigger_accuracy: 1.0       # v1: все триггер-тесты обязаны пройти
  compliance_pass_rate: 1.0   # снижать осознанно, по-сценарийно лучше flaky: true
```

### 4.1 Виды ассерций

| kind | Параметры | Проверяет |
|---|---|---|
| `file_exists` / `file_absent` | `path` | состояние воркспейса после прогона |
| `grep` | `glob`, `pattern`, `expect: present\|absent` | содержимое воркспейса (regex) |
| `transcript` | `pattern`, `expect` | regex по тексту транскрипта (например, «не предлагал коммит») |
| `git` | `expect: clean\|no_commits` | что агент не закоммитил / не нагадил в дерево |
| `judge` | `rubric`, опц. `evidence: transcript\|workspace\|both` | мягкие критерии через LLM-judge; judge обязан цитировать доказательство |

Детерминированные ассерции — предпочтительный инструмент; `judge` — для
критериев, которые нельзя выразить grep'ом (тон, «не дописал за пользователя»,
«задал ровно один вопрос»). Сценарий пройден, когда прошли **все** его ассерции.

### 4.2 Триггер-тесты: два уровня исполнения

- **L1 — selection-judge (дефолт, дёшево).** Без запуска Claude Code: judge
  получает prompt сценария + `description` **всех** скиллов библиотеки +
  вариант «ни один» и выбирает, какой скилл должен сработать. Это прямой тест
  качества и взаимной различимости описаний — того самого текста, по которому
  матчится реальный хост. Ошибка на негативном тесте = описание перетягивает
  чужие запросы.
- **L2 — headless-прогон (опционально, `--level 2`).** Реальный `claude -p` с
  установленной библиотекой-плагином; срабатывание скилла детектится по
  транскрипту (вызов Skill tool / маркер). Дороже и ближе к продакшену;
  используется выборочно и в nightly.

## 5. Раннер

### 5.1 CLI

```bash
cd installer
uv run python scripts/run_evals.py                      # все suites, уровень L1 + compliance
uv run python scripts/run_evals.py learning-mode        # один скилл
uv run python scripts/run_evals.py --validate           # только статическая валидация (без LLM)
uv run python scripts/run_evals.py --baseline learning-mode   # RED-прогон без скилла
uv run python scripts/run_evals.py --repeat 3 --json --report out.json
```

Exit-коды — конвенция основной спеки §8.2: `0` всё прошло, `1` есть
проваленные сценарии, `2` системная ошибка (нет API-ключа, сломан suite).

### 5.2 Архитектура (зеркалит Core/Wizard-разделение CLI)

```
installer/src/askill/evals/
  models.py      # pydantic: EvalSuite, Scenario, Assertion, Verdict, Report — extra="forbid"
  loader.py      # suite.yaml -> EvalSuite; контракт имён, version_tested vs SKILL.md
  asserts.py     # детерминированные ассерции (чистые функции над Path/транскриптом)
  scoring.py     # агрегация: вердикты -> метрики -> прошёл/не прошёл по thresholds
  report.py      # JSON-отчёт + человекочитаемая сводка (та же идея, что utils/output.py)
  transport.py   # ЕДИНСТВЕННАЯ граница с внешним миром: Protocol с двумя методами —
                 #   run_agent(workspace, prompt(s), budget) -> Transcript
                 #   ask_judge(rubric, evidence) -> Verdict
                 # реализации: ClaudeHeadless (subprocess claude -p), AnthropicJudge (API),
                 #   FakeTransport (юнит-тесты)
  harness.py     # сборка прогона: tmp-воркспейс <- фикстура; установка скилла из
                 #   локального дерева через core/installer (dogfooding archive-пути);
                 #   вызов transport; сбор артефактов
scripts/run_evals.py   # argparse-обёртка над evals.* (как generate_registry.py)
```

Требования те же, что к ядру CLI: mypy strict, ruff, юнит-тесты на
`models/loader/asserts/scoring` с `FakeTransport`, покрытие >80%. Сетевые/
subprocess-вызовы существуют только в `transport.py`.

### 5.3 Механика прогона комплаенс-сценария

1. Создать tmp-воркспейс; скопировать фикстуру (или пустой git-репозиторий —
   `git init` + один коммит, чтобы `git`-ассерции имели точку отсчёта).
2. Установить тестируемый скилл из рабочего дерева в project-scope воркспейса
   (через `askill.core.installer`, минуя сеть) — для baseline шаг пропускается.
3. Прогнать prompt (или последовательность `turns`; плейсхолдер
   `{{submit: ...}}` означает «сымитировать работу пользователя»: harness
   применяет описанное изменение к воркспейсу между ходами).
4. Собрать транскрипт + финальное состояние воркспейса.
5. Выполнить ассерции; judge-ассерции уходят в `ask_judge` с рубрикой и
   доказательной базой.
6. Вердикты — в `scoring`, отчёт — в `report`.

### 5.4 Бюджет и модели

- Бюджет сценария (`budget.max_turns`, таймаут) принудительно ограничивается
  harness'ом; вышли за бюджет → сценарий failed с причиной `budget-exceeded`.
- Модель прогона — из suite (`budget.model`); модель judge — параметр раннера
  (`--judge-model`, дефолт — дешёвая: `claude-haiku-4-5-20251001`); прогонная
  и судейская модели намеренно разные, чтобы judge не «подыгрывал» своему
  стилю.
- `--repeat N` повторяет каждый LLM-сценарий N раз и показывает разброс;
  пороги при этом применяются к худшему прогону (консервативно).

## 6. Методология baseline (RED → GREEN)

Правило для **новых** скиллов и для **существенных правок** тела скилла:

1. **RED.** Прогнать комплаенс-сценарии с `--baseline` (без скилла).
   Зафиксировать в `evals/<name>/BASELINE.md` краткую сводку: какие ассерции
   падают и как именно агент ведёт себя без скилла (3–10 строк, без полных
   транскриптов — они дороги в поддержке и быстро гниют).
2. **GREEN.** Прогнать те же сценарии со скиллом — все должны пройти.
3. **REFACTOR.** Каждую найденную «лазейку» (агент формально прошёл, но обошёл
   дух правила) закрывать парой: правка скилла + новая ассерция/сценарий.

Если baseline-прогон проходит ассерции И БЕЗ скилла — сценарий ничего не
проверяет: либо ассерции слабые, либо скилл не нужен для этого поведения.
Раннер помечает такие сценарии предупреждением `passes-without-skill` при
`--baseline`-прогоне.

## 7. Минимальное покрытие и статическая валидация

Обязательный минимум на скилл (проверяется БЕЗ LLM, командой `--validate`):

- suite существует и валиден по схеме (`extra="forbid"`);
- `skill` совпадает с именем папки, `version_tested` совпадает с текущей
  версией `SKILL.md` (расхождение — warning локально, **failure в CI**: правишь
  скилл → обнови или подтверди suite);
- ≥ 2 позитивных и ≥ 2 негативных триггер-теста (негативные обязаны включать
  хотя бы один кейс из «Do NOT use for…» самого описания);
- ≥ 1 комплаенс-сценарий с хотя бы одной детерминированной ассерцией;
- все `fixture`-ссылки разрешаются в существующие папки.

## 8. CI-интеграция

Двухконтурная, чтобы не вешать стоимость LLM на каждый PR:

1. **`ci.yml` (каждый PR)** — новый шаг в существующем workflow:
   `run_evals.py --validate`. Без сети и ключей; гарантирует, что suites есть,
   валидны и не отстали от версии скилла. PR, меняющий `skills/<name>/` без
   обновления `version_tested`, падает здесь.
2. **`evals.yml` (по требованию)** — отдельный workflow:
   - триггеры: `workflow_dispatch`, PR-label `run-evals`, weekly cron;
   - секрет `ANTHROPIC_API_KEY`;
   - на PR прогоняет только suites скиллов, затронутых диффом; cron — все,
     уровень L2 для триггеров;
   - отчёт JSON — артефактом workflow; сводка — комментарием в PR.

Прогон LLM-evals остаётся **рекомендованным, не обязательным** статусом для
merge в v1; обязательной является статическая валидация. Пересмотреть после
накопления статистики стабильности (флакучесть judge).

## 10. Открытые вопросы

1. **Язык сценариев.** Промпты сценариев — на английском (как тела скиллов)
   или зеркалировать оба языка для двуязычных триггеров? (v1: английский;
   отдельные русскоязычные позитивные триггеры — по желанию автора скилла.)
2. **Детект срабатывания в L2.** Надёжный маркер вызова скилла в транскрипте
   headless Claude Code (Skill tool call vs текстовый маркер) — уточнить по
   фактическому формату `--output-format stream-json` на момент реализации.
3. **Флакучесть judge.** Если pass/fail скачет, варианты: повышение
   `--repeat` c голосованием 2-из-3 только для judge-ассерций; фиксация
   рубрик; пер-сценарный `flaky: true` с отчётом, но без провала suite.
4. **`askill eval` как команда CLI.** В v1 — maintainer-скрипт; выносить ли в
   публичную поверхность CLI (для авторов скиллов в форках) — решить после
   фазы 2.
